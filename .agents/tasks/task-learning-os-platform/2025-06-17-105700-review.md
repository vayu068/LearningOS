# National Learning Operating System: AI-enabled EdTech Platform

This is a greenfield implementation of a multi-tenant EdTech platform targeting India's education DPI ecosystem. Built as a pnpm monorepo with Next.js 14 frontend, serverless Lambda backend, and 8 AWS CDK stacks, it covers adaptive AI tutoring, DPI integrations (APAAR, DigiLocker, ABC), DPDP-compliant consent management, and offline-first progressive web features across 7 Indian languages. The architecture uses DynamoDB single-table design for tenant isolation, Cognito for auth, and a provider-abstracted AI layer supporting Bedrock and OpenAI.

**Watch for:** AI providers ship with non-functional stub clients that throw at runtime (confirmed); registration handler allows any caller to self-assign any role including `super_admin` (confirmed); DigiLocker OAuth state token lacks HMAC integrity protection and is trivially forgeable (confirmed); tenant isolation relies solely on JWT claim comparison with no server-side enforcement at the data layer (confirmed); the in-memory rate limiter is the only implementation and cannot work across Lambda invocations (confirmed).

## High-level view

The multi-tenant model scopes all DynamoDB access by a `TENANT#` partition key prefix, which structurally prevents cross-tenant data leakage at the query level. However, the auth middleware's `validateTenantIsolation` is a simple string equality check that is never actually called inside the handler chain, leaving enforcement as a caller responsibility that can easily be missed.

The AI provider abstraction defines a clean `AIProvider` interface with Bedrock and OpenAI implementations, but both ship with placeholder clients that immediately throw. The `createBedrockRuntimeClient` factory returns a stub that raises "client not initialized," and the OpenAI `createDefaultHttpClient` does the same. There is no conditional gating or feature flag to surface these failures gracefully at startup rather than at first user request.

The DPDP consent layer is the most thorough subsystem: purpose limitation, data minimization, guardian consent for minors, withdrawal with audit trails, and expiry checks are all implemented. The gap is that DPI API handlers (ABC, APAAR) require a `consentId` header but don't actually verify it against the consent store, so any string satisfies the check.

Infrastructure stacks apply defense-in-depth: WAF with AWS managed rule sets, VPC flow logs, DynamoDB encryption, S3 block-public-access, CloudFront TLS 1.2 minimum, and separate security groups for Lambda and database tiers. The auth stack enforces MFA in production. The single weakness is that the Cognito pre-signup trigger validates tenant existence but has no access to DynamoDB to actually perform the check.

The offline/i18n frontend provides service worker caching, IndexedDB persistence, and an offline mutation queue. The sync queue has a conflict resolution gap: mutations queued offline replay in order but the server may reject stale writes with no retry differentiation from network errors.

<summary>Issues (8)</summary>

1. **Role self-assignment in registration** — The `register` handler accepts `request.role` directly from the caller and writes it to Cognito custom attributes without validation. Any user can register as `super_admin`. Restrict to `student` or require admin invitation for privileged roles.
2. **AI providers non-functional at runtime** — Both `BedrockProvider` and `OpenAIProvider` ship with stub HTTP clients that throw immediately. Either wire real SDK clients or add a startup health check that fails fast with a clear error instead of crashing on first user request.
3. **DigiLocker state token forgeable** — The OAuth `state` parameter is a plain base64url-encoded JSON object. An attacker can craft any `{userId, tenantId, timestamp}` payload. Sign the state with HMAC-SHA256 using a server secret and validate the signature in the callback handler.
4. **Tenant isolation not enforced at data layer** — `validateTenantIsolation` exists but is never invoked by any handler. Add middleware that automatically compares the authenticated user's `tenantId` from the JWT against the resource's tenant scope on every request.
5. **Rate limiter incompatible with Lambda** — `InMemoryRateLimitStore` resets on every cold start. Implement the `RateLimitStore` interface with DynamoDB atomic counters or ElastiCache Redis (the CDK security group already allows port 6379).
6. **Consent verification not enforced in DPI handlers** — ABC and APAAR handlers check for presence of `X-Consent-Id` header but never verify the referenced consent artifact is active, unexpired, and covers the requested purpose/data category.
7. **Offline sync conflict resolution** — The service worker and API client queue mutations and replay them, but there's no mechanism to handle 409 conflicts or stale-data rejections differently from transient failures. Failed syncs are silently re-queued forever.
8. **DynamoDB auto-scaling on PAY_PER_REQUEST** — The database stack sets `billingMode: PAY_PER_REQUEST` but then conditionally adds auto-scaling for prod, which only applies to provisioned mode. The scaling configuration is dead code in the current setup.

## Role escalation in user registration

The `createRegisterHandler` in `apps/api/src/handlers/auth/register.ts` accepts the `role` field directly from the request body and passes it through to Cognito's `custom:roles` attribute and the DynamoDB user record:

```typescript
UserAttributes: [
  { Name: "custom:roles", Value: request.role },
],
```

The `validateRegisterRequest` function checks only that `role` is present (`if (!request.role)`), not that it's a permitted value. A POST to `/auth/register` with `"role": "super_admin"` creates a super-admin account. The fix is either an allowlist (only `student` via self-registration) or a separate admin-only endpoint for privileged role assignment.

## AI provider stub clients

`packages/ai/src/providers/bedrock.ts` defines `createBedrockRuntimeClient` as a factory that returns an object whose methods throw:

```typescript
return {
  invokeModel: async () => {
    throw new Error(
      `Bedrock client not initialized. Configure AWS SDK with region: ${config.region}`
    );
  },
```

This means any call to `provider.complete()` or `provider.stream()` hits a retry loop that fails three times and then propagates the error. The code is structured for dependency injection but the production export at module level constructs the stub. Same pattern in `openai.ts` with `createDefaultHttpClient`. The real AWS SDK import (`@aws-sdk/client-bedrock-runtime`) is absent from `packages/ai/package.json` dependencies—this isn't a test seam, it's an incomplete integration.

## DigiLocker OAuth state forgery

In `apps/api/src/handlers/dpi/digilocker.ts`, the `authorize` handler builds the state token as:

```typescript
const state = Buffer.from(
  JSON.stringify({ userId, tenantId, timestamp: Date.now() })
).toString("base64url");
```

The callback handler decodes it and trusts the embedded `userId`/`tenantId`. An attacker who intercepts or crafts an OAuth callback can substitute any user's identity. The state parameter needs an HMAC signature appended and verified, or it should reference a server-side session ID stored in DynamoDB with a TTL.

## Tenant isolation enforcement gap

The `validateTenantIsolation` function in `apps/api/src/middleware/tenant.ts` compares two tenant IDs:

```typescript
export function validateTenantIsolation(
  requestTenantId: string,
  authTenantId: string
): boolean {
  return requestTenantId === authTenantId;
}
```

This is exported but grep across the handler files shows zero call sites. The DynamoDB key design (`PK = TENANT#{tenantId}`) provides structural isolation for reads, but any handler that writes data or reads by GSI2 (email lookup, which is cross-tenant) could bypass isolation if the authenticated tenant doesn't match the target. The middleware should be applied automatically in the handler wrapper rather than left as an opt-in call.

## Rate limiting in a serverless context

The `InMemoryRateLimitStore` class maintains a `Map<string, { count, resetAt }>` that lives only for the duration of a single Lambda execution context. Under real traffic, each cold start gets a fresh map, and warm instances don't share state. The `RateLimitStore` interface is well-designed for pluggable backends but no persistent implementation exists. The API Gateway stage already has burst/rate limits (100 burst, 50 rate) as a safety net, but the per-tenant/per-user granularity intended by the middleware is not achievable without a shared store.

## Consent header presence vs. verification

The ABC handler `getAccount` checks:

```typescript
if (!consentId) {
  return { statusCode: 403, ... };
}
```

But then proceeds to return account data without calling `ConsentManager.verifyConsentForProcessing`. The consent manager has full verification logic (expiry, purpose limitation, data category coverage, withdrawal check), but the API handlers treat consent as a boolean header presence check. This means a withdrawn or expired consent ID still grants access.

## Infrastructure: dead auto-scaling configuration

In `infrastructure/lib/database-stack.ts`:

```typescript
billingMode: dynamodb.BillingMode.PAY_PER_REQUEST,
...
if (props.stage === "prod") {
  const readScaling = this.table.autoScaleReadCapacity({ ... });
```

DynamoDB auto-scaling applies only to provisioned capacity mode. With `PAY_PER_REQUEST`, the `autoScaleReadCapacity` and `autoScaleWriteCapacity` calls will fail at deploy time with a CloudFormation error. Either switch prod to provisioned mode with auto-scaling, or remove the scaling block.

## Offline mutation queue replay

Both the service worker (`public/sw.js`) and the `ApiClient` class maintain offline queues. When the network returns, they replay mutations sequentially. If the server responds with a 409 (conflict) or 400 (validation failure due to stale state), the client treats this the same as a network error—the service worker's `syncQueuedRequests` catches the error and logs "Sync failed," keeping the item in the queue. This creates an infinite retry loop for permanently-failed mutations. Mutations that receive a 4xx response should be removed from the queue and surfaced to the user.

## Cognito triggers as inline code

All four Lambda triggers in the auth stack use `Code.fromInline(...)` with stub implementations. The pre-signup trigger attempts to validate tenant existence but has no DynamoDB client or table reference—it can only check that the metadata field is non-empty. For production, these need real implementations bundled from the `apps/api` package with proper IAM permissions to query the database.
